# Cloud Quran

Free, open-source, waqf-funded Quran reading app — iOS, Android, Web, Desktop. No ads, no tracking, no monetization.

## Source of truth

**`~/Ship/wisdom-fruits` is the canonical reference for every stack and convention decision.** Cloud Quran's platform is a fork of it (2026-08-19). When something here is ambiguous, look there first — do not re-derive it.

⚠️ **`~/Ship/wisdom-stack` is stale — never use it.** It still prescribes bun, NativeWind, D1 + Drizzle + Better Auth and Tauri, and its README instructs replacing InstantDB with D1. It predates the 2026-05-20 replatform.

## Stack

pnpm + Turborepo (`nodeLinker: hoisted`) · Expo SDK 56 · RN 0.85 · React 19.2 · `@expo/ui` + RN StyleSheet · Expo Router with our OWN header and tab bar drawn in the RN view tree (architecture §9, third flip 2026-08-27 — `NativeTabs` and the native stack header are out; story 6-6 landed the migration: `components/ui/AppHeader` + `AppTabBar`) · **Cloudflare D1 + Drizzle + Better Auth behind the Hono worker** · Cloudflare R2 (audio) · Electron desktop · Astro marketing · MMKV · expo-audio · Biome · jest-expo + RNTL · sops + age · opt-in Sentry.

**Not used, deliberately:** InstantDB, any reactive sync engine, Tauri, NativeWind, RevenueCat, Paddle, PostHog. **Story 5-2 removed all three of the inherited ones outright** — no imports, no dependencies, no config keys, no CSP origins.

⚠️ **Identity exists as of story 5-5 — Better Auth on the worker, anonymous-first.** The app mints an anonymous session from an effect in the root layout and **nothing waits for it**: every reading surface works with no identity at all, and an offline first launch is a silent no-op that retries next time. Never gate the first frame on a session; `root-layout-boot.test.tsx` and `lint-layers.mjs` both scan for the shapes that would.

Sign-in has ONE entry point, `(tabs)/(profile)/sign-in.tsx`, which is why story 5-7's FR30 disclosure could be put in one place and be complete.

⚠️ **The client data layer landed in story 5-6: `lib/sync.ts` (queries) + `lib/outbox.ts` (writes).** Reads are `@tanstack/react-query` seeded **synchronously** from MMKV via `initialData`, so an offline cold launch paints last-known state on the first render — there is no persist-client, deliberately, because its restore is asynchronous and that is a boot gate under another name. Writes never call the API: they update the local cache, then land in a durable MMKV outbox that coalesces (one pending entry per LWW entity, newest `updatedAt` wins), debounces, and drains oldest-first on reconnect or foreground, answering one of four verdicts per entry (`sent`/`drop`/`retry`/`halt`). **A mutation invalidates explicitly** — the one thing the retired reactive database did for free. Query keys and MMKV keys both carry the user id, so a session change re-keys rather than leaking; `accountTeardown` clears the outbox anyway, because a queued write carries no identity and would drain into the NEXT account. `app/_layout.tsx` mounts `QueryClientProvider`, wires TanStack's `onlineManager`/`focusManager`, and mirrors the resolved session id into the query keys from a null-rendering bridge — `lib/sync.ts` must never import `@/lib/auth` itself (`auth → accountTeardown → sync` is a fixed chain, so that edge closes a require cycle).

⚠️ **The Quran text has a SECOND client data path, and it is deliberately not the query module: `lib/quranDb.ts` (story 6-1).** `lib/sync.ts` + `lib/outbox.ts` own state the WORKER owns — they seed from MMKV, coalesce writes and invalidate explicitly, all of which answer "the server has a different copy". The Quran text has no server copy: it ships in the bundle, never changes at runtime, and is identical for every reader, so putting it behind the sync client would key it by USER ID and make an account purge look like it could delete the Quran. `quranDb.ts` imports the bundled asset into the SQLite directory once, opens it, runs `PRAGMA query_only = ON`, maps snake_case columns onto `quran-data`'s camelCase types, and exports **only** `getSurahVerses` / `getSurahMetadata` / `getVersesForPositions` (6-4's preview join) — never the handle. `lint:layers` rule 8 keeps it the only door. ⚠️ **Every read is async on purpose**: `expo-sqlite@56`'s web backend serves `*Sync` calls over a `SharedArrayBuffer` and writes the result's byte length with `Uint8Array.set(Uint32Array)`, which writes ONE byte — so every sync result is truncated to `length & 0xFF`. Measured in the browser: Al-Fatihah's ~1,800 bytes arrived as 8. The async methods do not use that channel. The feature-level wrapper is `features/reading/hooks/useSurah.ts`, which turns a failure into a VALUE (a real error surface with a retry) rather than a thrown promise.

⚠️ **The reading surface is `app/(tabs)/read.tsx` (story 6-1; a TAB ROUTE since 6-6), and its load-bearing shapes are:** chrome starts **hidden** and is revealed by an RNGH `Gesture.Tap()` over the whole reading area — not a `Pressable`, which takes the RN responder on touch start and blocked scrolling outright, and not a per-row press, which left no "elsewhere" to tap and spent the verse tap epic 7 is promised. The tap carries `.cancelsTouchesInView(false)` so it cannot cancel the `Pressable`s inside it. The reading position is written **once per verse change** through `lib/usePosition.ts`, which holds the comparison so no screen can write per tick; the saved `(surah, verse)` pair is clamped **as a pair** into the book and re-resolved only on FOCUS (`useFocusEffect`) — that resync is what makes the chrome's mushaf↔reading toggle mean "same place, different renderer", and its restore-latch guard asks the ROWS which surah they belong to, never the prop echo (the stale-rows commit consumed the latch once). The web-only Uthmani face is a **second, non-gating `useFonts`** (`UTHMANI_WEB_FONT` in `constants/arabic.ts`): in the boot map its error is rethrown into the router's ErrorBoundary, so a 237 KB font fetch failing took the whole web app down. ⚠️ **The family name differs per platform** — iOS/web want the font's internal family (`KFGQPC HAFS Uthmanic Script`), Android wants the asset FILENAME — and a wrong value renders in the system font silently.

⚠️ **The mushaf surface is `app/(tabs)/index.tsx` (story 6-2; since 6-6 it is THE HOME SURFACE — the tab group's index, serving `/` directly with no redirect in front) — one chrome driver, the same RNGH tap, and the same focus resync as `read.tsx` (the restore latch re-arms per resync so a resync landing never writes).** Its pager is a **reversed-data** `[604..1]` FlashList (`horizontal`+`pagingEnabled`, never `inverted` — the pre-fork measured `inverted` breaking web drag), so advancing lands on a lower index = higher page, the RTL turn. `initialScrollIndex` IS allowed here — 6-1's ban was about variable-height verse rows; a mushaf page is a uniform full-screen item, so index × width is exact. The saved pair is resolved **as a pair** through `getPageForVerse` (−1 → page 1), and the position write is one per **settled page** — `getFirstVerseForPage` through `usePosition('mushaf')`, whose comparison is the throttle, plus a one-shot restore latch so *opening* writes nothing (page 42's first verse is 2:253; writing it would clobber a saved 2:255). ⚠️ **Verse identity comes from `words[].location` only, never `verseRange`** — 565 committed lines carried a drifted `verseRange` until this story regenerated the layout data (delta verified `verseRange`-only; `generate-verse-page-map.ts` output unchanged). ⚠️ **The pre-fork page component crashed on every load** (`useCallback` after two early returns, swallowed by an ErrorBoundary): today's `MushafPage` calls every hook before its first return, the line renderer is hookless (styles arrive as a prop), and `MushafPage.test.tsx` renders the loading→loaded transition with the REAL renderer — the pre-fork harness stubbed hooks, which is how the crash shipped unobserved. The data's basmala rows carry **no glyph** — `BASMALA_TEXT` in `constants/mushaf.ts` IS the render, in the KFGQPC text face; `word.qpcV1` is QPC glyph encoding, so the U+06DF strip does **not** apply here.

⚠️ **The Quran index is `app/surahs.tsx` → `features/quran-index/` (story 6-3): a pushed ROOT route (never a tab — the table grew to four with Bookmarks in 6-4, but the index stays a PICKER, not a destination), opened from the chrome's title on both reading surfaces, and a selection is WRITE → BACK → FOCUS RESYNC, never navigation-with-params.** The index calls `reportVerse(surah, verse)` ONCE through `usePosition(mode)` and pops; the surface underneath re-resolves the saved pair on focus (6-6's mechanism) and jumps. A param-carried target would be a second position channel — the decoupling `usePosition` exists to prevent. Tapping the CURRENT surah's row writes nothing (a `(surah, 1)` write would clobber the saved verse); juz'/hizb rows navigate by their `(startSurah, startVerse)` pair, never page arithmetic. ⚠️ **`JUZ_METADATA`/`HIZB_METADATA` carry NO stored page column — 6-3 deleted it.** The old `startPage` was an arithmetic ladder (56/60 hizb values exactly `10n − 8`), not a reading of any mushaf, and it mislabelled 27 of 604 page headers; the page is derived via `getPageForVerse(startSurah, startVerse)`, so the two halves agree by construction and `juz-hizb-metadata.test.ts` pins that the column stays gone. The prev/next footer is `SurahNavigator` (both ends wrap, 114→1 and 1→114). ⚠️ **The welcome-back banner (`WelcomeBackBanner`, home surface, saved row ≥7 days old) sits BELOW the header zone — `top = insets.top + CHROME_BAR_HEIGHT + SPACING.sm`, pinned by test** (the pre-fork's `insets.top + spacing.sm` is the recorded `welcome-banner-overlap` defect) — **and it is NOT chrome**: it never touches `useChromeReveal` (its own fade is the ONE documented by-filename exclusion in `ReadingChrome.test.tsx`'s one-driver walk), and it dismisses at 4s or on the first real page move, never on the restore settling.

⚠️ **Bookmarks are story 6-4, and the UI is the WHOLE story — the data path predates it.** The worker table with union-merge on `(user, surah, verse)`, the client hooks (`useBookmarks`) and mutations (`addBookmark`/`removeBookmark`, ids client-minted via `Crypto.randomUUID()` at the call site), and the outbox kinds all shipped in 5-4/5-6; 6-4 added no merge logic anywhere. The toggle lives in **`VerseRow`'s meta row** (control left, ayah badge right — the pre-fork shape): filled state `accent.primary` on `background.primary` (measured ≥ 4.05:1 on 2026-08-28; the pin in `palettes.contrast.test.ts` holds the WCAG bar, ≥ 3:1 — a palette at 3.5 passes it), outline `text.secondary`, indicator immediate because `addBookmark` applies the cache synchronously. **The toggle reports the ROW's own `(surah, verse)` pair, never the screen's current-surah ref** — `showing.current` moves synchronously while the old surah's rows are still tappable during a resync's async load, and reading it minted wrong-surah bookmarks (6-4's review). Its press ALSO toggles chrome — the surface tap is RNGH, `stopPropagation` cannot reach it; named and accepted in the spec. The **Bookmarks tab is the fourth `TABS` entry** (`(tabs)/bookmarks.tsx` → `features/bookmarks/`; `TABS[0]` stays the mushaf), NOT immersive — `AppHeader` + `AppTabBar` occupy layout, no `useChromeReveal` (pinned by source scan). A row tap is 6-3's mechanism verbatim: ONE `reportVerse` through `usePosition('reading')`, then a macrotask-deferred `router.navigate(READ_HREF)` — read.tsx's focus resync lands the reader; never navigation-with-params. Arabic previews come through **`getVersesForPositions` in `lib/quranDb.ts`** (rule 8's one door — row-value `IN`, chunked at 400 pairs against SQLite's compile-flag parameter ceiling, `[]` without opening for empty input), joined in `features/bookmarks/hooks/useBookmarkRows.ts`, which re-queries only when the key-set string changes and NEVER drops a row (an orphan pair keeps its row, preview absent). The U+06DF strip is now `stripDisplayMarks` in `constants/arabic.ts`, shared by `VerseRow` and the preview. In-row delete is the neutral `RowDeleteButton` — **the pre-fork's `Swipeable` + red Delete is superseded** (23.13's standard; red belongs on confirmations, removes are trivially reversible), recorded in `_reference/README.md`.

⚠️ **Mushaf fonts are per-page (`QCF_P{NNN}`), fetched on demand from the app's OWN CDN and cached in the DOCUMENT directory — `lib/mushafFonts.ts` is the only loader.** `cdn.nobleachievements.com/fonts/qpc-v1/` (R2 `gp-cdn`, uploaded by `scripts/prepare-fonts.ts` from `nuqayah/qpc-fonts` at a pinned SHA), **never `raw.githubusercontent.com`** — a per-page fetch discloses which pages a reader opens, and only Cloudflare is a named processor. ⚠️ **THE FORMAT IS PER-PLATFORM AND IT IS A CORRECTNESS SWITCH, NOT A SIZE ONE: native fetches `.ttf`, web fetches `.woff2`.** Android's `Typeface` loader cannot parse WOFF2 **and `Font.loadAsync` resolves anyway** — so every mushaf page drew in the system fallback, which for QPC V1 means the U+FB51-based glyph codepoints render as their literal Unicode meaning: disconnected Arabic letters that read as plausible Arabic but are **not the Quran**. Measured on a Pixel 9 Pro 2026-08-28 with the correct file on disk, byte-identical to the CDN's; fixed at `955dcba`. The CDN carries both formats for all 604 pages. **Patched fonts win before any platform or network branch**: pages 154/161/166/302/472/566 ship repaired copies in `assets/fonts/qpc-patched/` (**TTF — a bundled woff2 would re-open the Android bug on exactly the six pages that are supposed to be the offline-safe ones**; the dir keeps a woff2 copy too, only so the CDN mirror is correct in both formats) because upstream glyphs have degenerate contours Safari/CoreText render *invisible*. The disk cache is the document directory, not `Paths.cache` — the cache directory is OS-evictable and an evicted font is a broken offline promise. Layout data is the other half: `lib/mushafLayout.ts` lazy-`require`s the 7.8 MB monolith **inside** the accessor, so the parse is paid on first mushaf open, not at boot. An uncached page offline is a page-level retry surface (chrome revealed for the visible page only), never a blank screen — and that reveal is checked on **both** edges, because a page usually fails while it is still an off-screen neighbour and only becomes visible afterwards.

⚠️ **`MUSHAF_GLYPH_SCALE` is 0.06 and it is MEASURED, not a taste knob — a wrong value silently destroys the facsimile.** The glyph size is that fraction of the container width; too large and every line wraps to a second visual row, so 15 data lines become ~28, the column overflows and the page number is drawn through the last line. The pre-fork's `{ native: 0.065, web: 0.059 }` was inherited from a component that **crashed on every load**, so nobody had ever seen it render — 0.065 wraps. The ceiling comes from laying out all 8,820 text lines in Chromium with their own `QCF_P{NNN}` faces: the widest line in the book (page 254 line 13) wants 15.92× the font size, i.e. a maximum scale of 0.0628. ⚠️ **The measurement only holds while the WHOLE line is in the page face** — `MushafPage` sets `fontFamily`/`fontSize` on the line's `Text`, not only on each word's, because the `' '` separators are raw children that inherit the parent and would otherwise be system-font spaces at RN's default 14pt. ⚠️ **The size is the SMALLER of the width-driven ratio and a HEIGHT cap** (`MUSHAF_HEIGHT_BUDGET = 0.86`, 15 lines always) — width binds on a phone in portrait and height binds on any window wider than it is tall; without the cap an iPad in landscape drew a page several times too large to read, measured on the simulator.

⚠️ **The reading look is SIX palettes on TWO INDEPENDENT AXES, and the picker is `(tabs)/(profile)/appearance.tsx` (story 6-5).** ⚠️ **This paragraph described the opposite for one commit and the review caught it — do not trust a remembered version of it.** Story 6-5 first shipped a FOUR-way coupled control (System/Light/Sepia/Dark), cut the palette set to `['terracotta','sepia']`, and made sepia force `themeMode: 'light'`. The owner reversed all three the same day, and the reasoning is worth keeping: the five deleted palettes were removed as *"unreachable — `setPalette` had zero callers"*, which was true right up until 6-5, **and 6-5 is the story that makes them reachable.**

**What ships: `terracotta, sepia, linen, contrast, olive, midnight`** — Warm, Parchment, Paper, High contrast, Green, Night — **each with a REAL light AND dark slice**, so `sepia × dark` is a look a reader can actually reach. A six-swatch strip sets the palette; a separate System/Light/Dark control sets the scheme; neither touches the other. `ColorScheme` is still exactly `'light' | 'dark'`. **The "sepia forces light" coupling is DELETED and must not come back** — it does not generalise past one palette, and with six it would mean four palettes silently overriding the reader's mode.

**Palette is DEVICE-LOCAL (MMKV), which is why the picker needed no worker change**: `apps/worker/src/lib/validate.ts` still accepts exactly `['light','sepia','dark']`, with no migration. `wireTheme(palette, resolvedScheme)` coerces six palettes onto those three.

**The migration for a stored `'cobalt'` is that there is none** — `lib/theme.ts`'s `isPaletteName` guard validates against `PALETTE_NAMES` and falls back to `terracotta`; `theme.test.ts` pins it. Do not add a rename table.

⚠️ **The six were AUTHORED AGAINST THE GATES, not by eye** — every candidate run through all eleven contrast rules plus the focus-ring split (some slices must defeat a white-only ring, others a black-only one, none both) before a line was written. The gate went from 50 cases to 154. ⚠️ **Sepia's accent is `#A8472A`, deeper than terracotta's `#C65D3B`, and that is the CONTRAST GATE talking, not taste** — parchment is a lighter ground, so the default accent measures 4.17 white-on-accent (the 4.5 bar every non-terracotta palette is held to) and 2.59 against the tab-bar selection indicator. Tune the hue, never the bar.

⚠️ **A MALFORMED HEX DOES NOT ERROR, IT SCORES.** The first authoring pass reported zero contrast failures while containing `#9A8straight` — `parseInt('8s', 16)` is `8`, so a typo yields a plausible ratio rather than a throw. Validate colour FORMAT before measuring anything. Same family as `Font.loadAsync` resolving on a font Android cannot parse: the dangerous failures produce a believable value instead of an error.

⚠️ **Theme is mirrored TO sync and never applied FROM it.** Rendering stays device-local (MMKV via `lib/theme.ts`); a selection writes the coerced wire value through `patchPreferences` only when that coarse value actually MOVES (six palettes collapse onto three, so olive→linen writes nothing) so the worker's NOT-NULL `theme` column is honest — **System sends the RESOLVED scheme**, because `'auto'` is not one of the column's three literals. There is **no server→device reconciliation effect** and adding one is a loop with real failure modes (write → drain → invalidate → pull → re-apply). The whole-app crossfade is `components/ui/ThemeCrossfade` mounted in `app/_layout.tsx`: opacity 0.4 → 1 over `DURATIONS.theme` (400ms), **animating only on a subsequent `(palette, colorScheme)` change** — it mounts at opacity 1, because a fade on mount is a dimmed first frame, i.e. a boot gate wearing an animation's clothes. Reduce-motion is honoured by doing nothing (Reanimated's default `ReduceMotion.System`).

⚠️ **`patchPreferences` in `lib/sync.ts` is the partial writer, and 6-5 is the FIRST UI that ever wrote the preferences entity** — the epic-5.6 obligation, driven. The wire format has **no partial update** (`parsePreferences` validates all seven fields on every PUT), so it merges onto the current row — **query cache first, MMKV second, `DEFAULT_PREFERENCES` last**, the `visibleRows` doctrine — and names the seven fields one at a time rather than spreading the row, because `userId` and a stale `updatedAt` must never reach the body. ⚠️ **`DEFAULT_PREFERENCES.reciterId` is `'alafasy'`, never `''`** — the worker's `shortString(reciterId, 64)` is 1–64 characters, so an empty string is a 422 the drain drops, silently losing a reader's first change. The font-size slider writes **live** on `onValueChange` (the wrapper deliberately exposes no `onSlidingComplete` — 17.3's accepted regression), which is safe because the cache apply is synchronous, the outbox coalesces LWW, and the drain debounce restarts per write: a whole drag nets ONE PUT. A **same-value guard** on top of `step={2}` is what stops step-boundary jitter from re-rendering every verse row.

⚠️ **`lib/syncCache.ts` is the query module's network-free half, and it exists only to break that cycle.** It holds the device cache, the `QueryClient`, the user-id mirror and `clearSyncState`; `lib/accountTeardown.ts` imports it DIRECTLY, because reaching it through `lib/sync.ts` would drag `lib/api.ts` — and therefore `lib/auth.ts` — back into the loop. Metro found that cycle at the first device launch of story 5-6, after typecheck, lint and the whole suite had passed over it. It is a **gate subject, not a hole**: rule 7 lets only `lib/sync.ts` and `lib/accountTeardown.ts` import it, and `lib/sync.ts` re-exports only what a caller legitimately needs (the hooks, the mutations, `queryClient`, the user-id helpers, `clearSyncState`) — never `syncStore`/`readCache`/`writeCache`, which would hand a feature the same bypass under a blessed name. `@/lib/outbox` is guarded the same way, for the same reason: its singleton reaches the worker with no cache update, no invalidation and no debounce.

⚠️ **All three methods are offered on all four platforms, and only the MECHANISM varies** (owner renegotiated the frozen intent, 2026-08-25). iOS and Android use native ID tokens; Web and Desktop use Better Auth's OAuth redirect. **No screen may branch on `Platform.OS` to remove a method** — only to change how it is performed. `__tests__/app/sign-in-parity.test.tsx` renders the sheet as each platform and counts the buttons; `lib/auth.test.ts` pins which mechanism each platform picks, both directions.

⚠️ **Apple's web client secret is a JWT the worker SIGNS from a .p8** — Apple issues no static secret and caps the assertion at six months. `lib/appleSecret.ts` mints a short-lived one per use, so nothing expires; a pre-generated `APPLE_CLIENT_SECRET` is supported as a fallback and its expiry IS checked. An unusable credential is a typed `APPLE_WEB_SIGN_IN_UNAVAILABLE`, never a 500, and `GET /health` reports every leg's readiness plus the expiry date.

**All six legs are configured as of 2026-08-25** — Apple native + web (Services ID and .p8 are in the worker store; the worker MINTS the client secret per use, so nothing expires), Google native + web, and email OTP (`no-reply@cloudquran.nobleachievements.com`). `GET /health` reports each leg's readiness and the Apple assertion's expiry; trust it over any prose, including this line. The web app is served from `cloudquran.nobleachievements.com` and the worker from `api.` — same registrable domain, which is what makes the OAuth state cookie work.

⚠️ **ONE HUMAN, ONE ACCOUNT: every sign-in goes through `signIn.social`, and `linkSocial` is never called** (owner renegotiated again, 2026-08-25, after a production defect). `/link-social` compares the provider email only against `session.user.email` and never asks whether it belongs to somebody else — so a guest signing in with an address an existing account holds gets the provider attached to the ANONYMOUS user, and the reader ends up with two accounts. `/sign-in/social` resolves by verified email (`handleOAuthUserInfo` → `findUserByEmail`) and is in the `anonymous()` plugin's hook matcher, so `onLinkAccount` → `reassignUserRows` MERGES the guest's rows into whichever account they land in — union on bookmarks `(surah, verse)`, last-write-wins on the three single-row tables.

The only reason `linkSocial` was ever used is that `@better-auth/expo` attaches the stored cookie solely on paths ending `/link-social` — a CLIENT-side path check. `apps/expo/src/lib/auth.ts` attaches the cookie itself, so the same route serves native, web and desktop. **Re-adding `linkSocial` re-opens the duplicate-account bug**; `lib/auth.test.ts` asserts it is never called.

⚠️ **`user.email` is set by upstream, not by us.** The worker's account-create hook and `adoptProviderEmail` are DELETED — they existed only because `/link-social` leaves the user row untouched. `requireLocalEmailVerified: true` is set explicitly: every path this app ships proves the address it stores (OTP is inbox control, Apple and Google assert verified, a guest's `temp@` is unclaimable), so no unverified real address can exist here.

⚠️ **i18n IS used.** Story 5-1's Design Note 2 reversed the earlier "i18n out of scope" call: i18next and `lint:i18n` arrive with the seed already green, so removing them is work and retrofitting `t()` across finished Quran screens is much more work. The app keeps the infrastructure and ships **exactly one locale** (`EXPOSED_LANGUAGES = ['en']`, PRD NFR29). The inherited `es`/`fr` bundles stay on disk to keep the parity gate meaningful; they are not offered in the picker.

⚠️ **UI copy has a 120-character budget per string, enforced by `lint:i18n` in EVERY locale** (owner, 2026-08-26: "summarise text app wide and have it as a practice"). Checking English alone is what lets a translation overflow — `fr` runs 1.20× `en` here. A red budget is answered by cutting the string or moving the detail behind a link the reader chooses, never by relocating the wall to the next screen and never by raising the number; `COPY_BUDGET_ALLOWLIST` ships empty and an entry has to argue that the length is doing work. The reasoning lives in `~/dotfiles/claude/stack/i18n.md`, not here.

⚠️ **The build-time data pipeline is Node 24, and Bun is gone (story 5-3).** All six `scripts/*.ts` run under `node` directly — `node:sqlite`, `node:crypto`, `node:child_process`, `import.meta.dirname`. Two traps the port left comments on: `node:sqlite` **silently ignores unknown constructor options**, so Bun's `{ readonly: true }` opens the Quran database read-WRITE — only camelCase `{ readOnly: true }` refuses writes; and value imports of a `.ts` file need the explicit `.ts` extension, which Bun did not. `"engines": { "node": ">=24" }` is now load-bearing: `node:sqlite` did not stabilise before it.

⚠️ **The reader now has a full data lifecycle, and the three promises are DIFFERENT (story 5-7).** Export (`GET /api/account/export`) changes nothing. "Delete my synced data" (`POST /api/account/data`) empties the four tables and KEEPS the account. "Delete my account" is **Better Auth's own `POST /api/auth/delete-user`** — the 501 `POST /api/account/delete` stub was DELETED rather than filled, so there is one door, and its `beforeDelete` hook calls the same `purgeUserData` FR28 uses. All three are on one screen, `(tabs)/(profile)/data.tsx`. Four things that look like details and are not: **`session.freshAge: 0`** (upstream refuses `/delete-user` on a session older than a day without a PASSWORD, and no account here has one — the default makes in-app deletion impossible, which Apple 5.1.1(v) forbids; it is a SESSION-WIDE setting and also disables freshness on `/unlink-account` and `/list-sessions`, neither of which this app calls); **a purge KEEPS the `write_budget` row while a deletion takes it** (`PurgeScope`, no default — resetting the counter on a purge hands back a fresh daily ceiling for one request, and the purge is metered as ONE write rather than as the rows it destroys); **the client cancels in-flight reads, THEN clears the outbox, THEN the caches** — a late GET repaints what the purge destroyed, and a queued write drained afterwards re-creates it; and **a returned error from `/delete-user` is a REFUSAL, believed as one**, while only a thrown one (no answer at all) triggers a session re-check, taken with the cookie cache bypassed. Deletion runs server-first, device-second — the reverse of `signOut` — so a failure leaves the reader signed in with their pending writes intact, and both local halves swallow their own failures because by then the irreversible half has succeeded.

⚠️ **There is NO consent screen, and the opt-out is a switch (FR30, owner-amended 2026-08-26).** Reading position reveals religious practice — special-category under GDPR Art. 9 — and story 5-7 first answered that with a `consent.tsx` step in front of sign-in. It was deleted the same day: **sync already ran for the anonymous guest minted at boot** (`SyncIdentityBridge` → `prefetchSyncReads()`, four authenticated GETs per launch) and nothing in `lib/sync.ts` or `lib/outbox.ts` read the consent record, so the screen interrupted the one reader who chose to sign in and protected nobody. What stands: the **disclosure is inline above the provider buttons on `sign-in.tsx`** (four entities, both processors, that it is optional — pressing a provider is the affirmative act), and the **opt-out is a device-local switch, default ON** (`SYNC_ENABLED_KEY` in `lib/privacyPrefs.ts`, surfaced on `data.tsx`) which `lib/sync.ts` reads in the three places sync happens: `prefetchSyncReads()`, `drainNow()` and `useSyncQuery`'s `enabled`. Turning it off stops reads and drains, destroys nothing and signs nobody out — queued writes wait in the outbox. Do not reinstate a consent step; the owner's rule is that privacy must not cost the reader an interruption.

⚠️ **`sendDefaultPii: false` does not strip the `Authorization` header, and never did.** `lib/telemetryScrub.ts` scrubs `Authorization` / `Cookie` / `Set-Cookie` **unconditionally** — by key, whatever the value's type, and inside prose where no key exists — and `errors.ts` sets `sendDefaultPii: false` explicitly on top. The scrubber used to return `{}` whenever no content host was configured, which switched the whole scrub off on dev, test and any build without `EXPO_PUBLIC_CONTENT_URL`; it now always returns all four hooks. Proven by searching a **real serialized envelope** (`createEventEnvelope` + `serializeEnvelope`) for the credential, with an anti-vacuity case that the same event unscrubbed does carry it.

⚠️ **Recitation playback is story 7-1: `features/audio/hooks/useRecitationEngine.tsx` (the engine), `lib/reciterManifest.ts` (the lookup), and a REWRITTEN `stores/audioPlayerStore.ts`.** ⚠️ **Epic 7's own text says "almost all of this is already built". That is true of wisdom-fruits and FALSE of this tree** — story 5-1 deleted `features/player` (its ~7,800 lines still live next door, coupled to entitlements, analytics and the retired vendor; adapt the shape, never the dependencies). What survived and did the heavy lifting: the 1,583-line `patches/expo-audio@56.0.11.patch` (it is what gives `AudioPlaylist` `setActiveForLockScreen` / `updateLockScreenMetadata` at all), the 40-reciter catalogue, and `scripts/prepare-audio.ts`'s already-published CDN output.

**A queue entry is a SURAH.** `playSurah(n)` builds the playlist as surahs *n…114* with `loop: 'none'`, so auto-advance, the scrubber and **stopping at the end of An-Nas instead of wrapping to Al-Fatihah** all fall out of the native player rather than out of code. Advancing an ayah is a `seekTo` INSIDE the current track, never a track change. ⚠️ **`updateInterval` must be passed explicitly — it defaults to 500ms and the criterion is 100ms.** ⚠️ **The player speaks SECONDS and the manifest speaks MILLISECONDS**; that conversion exists on exactly two lines of the engine and must not spread. ⚠️ **The store publishes `activeVerseKey` and only on a CHANGE** (`lib/usePosition.ts`'s discipline, same reason) — both surfaces subscribe to that one field, so ten ticks a second cost ten comparisons rather than ten re-renders of Al-Baqarah. Listening position is written at EVENTS — pause, stop, track change, backgrounding — and both reading surfaces stop reporting reading position while playing, because an advancing recitation is exactly the "one write per verse change" shape that burned a day of the write budget pre-fork.

⚠️ **THE PUBLISHED TIMING DATA HAS A HOLE AND IT IS IN THE DEFAULT RECITER.** Audited across all 40 reciters 2026-09-02: 38 are complete (0/6,236 missing), **`alafasy` is missing 1,088 rows across 36 surahs** (Ya-Sin 81 of 83) and `abdulkareem` 305 — and `alafasy` is `DEFAULT_PREFERENCES.reciterId`. ## Non-negotiables

- **A test whose expected value is derived from the thing under test proves nothing.** ⚠️ **This is
  here because it has now bitten TWICE in four days, in unrelated files** — the bar for a permanent
  rule. (1) `web-focus-ring.test.ts` looped all twelve palette slices asserting
  `max(contrast(#fff, X), contrast(#000, X)) >= 3`; that holds for every colour in the sRGB cube —
  the true floor is 4.58 — so it could not fail for any hue edit, or with the palettes deleted,
  while its docblock said "MEASURED, not assumed". (2) `MushafPageHeader.test.tsx` computes its
  expectation as `` `Juz' ${getJuzForPage(40)} · Hizb ${getHizbForPage(40)}` `` — the very functions
  under test, so the ~28 page labels story 6-3 moved are unobserved. **The check:** ask what edit
  would redden this, and if the honest answer is "none", it is a restatement, not a test. A literal
  expected value, or a mutation you actually ran and recorded, is the fix. (Rescued from
  `stack/gates-scanners.md`, deleted 2026-08-27 — the other seventeen rules in that shard stay
  deleted until they bite twice too; a rule nobody has been burned by is a tax on every later read.)

- **Quran text integrity.** SHA-256 per ayah of `uthmani_text`, verified at build time by `pnpm verify` (which `pnpm test` now runs first). A mismatch fails the build. No runtime path mutates Quran text.
  ⚠️ **THE COVERAGE GAP IS CLOSED (2026-08-28) — this paragraph used to warn that it was not.**
  `pnpm verify` is now two gates chained: `verify-quran.ts` (per-ayah SHA-256 of `uthmani_text`,
  6,236 hashes, pinpoints the verse) then `verify-artifacts.ts` (one digest per artifact for the
  five things the first one never touched — `verses.simple_text`, `translations`,
  `surah_metadata`, the 604 mushaf layout files, and the generated verse↔page map). Artifact
  digests rather than per-row hashes on purpose: `hashes.ts` is already 484 KB for ONE column, and
  a build gate has to answer "did the generated data change", which is acted on by regenerating,
  never by patching a row. **Every artifact also declares the size the Quran fixes it at**, because
  a digest cannot see truncation — an empty table hashes to a perfectly stable value. Mutation-
  checked both ways: one appended space in the translation of 2:255, and one reserialized layout
  file with identical data, are each caught and named.
- **Offline-first is the default path**, not a fallback. Network is enhancement only.
- **Zero third-party analytics, advertising or tracking SDKs.** Opt-in, PII-scrubbed Sentry is the only exception — and as of story 5-2 that is an actual opt-in gate (`lib/privacyPrefs.ts`, default OFF), not merely an unconfigured DSN. There is no analytics vendor and no database vendor to name as a sub-processor any more; Cloudflare is a processor under GDPR Art. 28 (the worker and D1 since story 5-4, R2 before that). Since story 5-5 the only other party that ever sees a user is the identity provider that user chose themselves.
- **No monetization surface.** If a ported module carries one, delete it rather than disable it.
- **Cost floor $0–5/month** — a target, not a veto. ⚠️ **"Stay structurally off the paid tier" stopped describing reality around 2026-07** (owner-confirmed 2026-08-24): the account is on **Workers Paid**. Two claims that followed from the old premise are wrong wherever they still appear — a Cron Trigger does **not** require Paid, and D1's write budget is the Paid one (50M rows/month, **billed**) rather than the free tier's 100k/day **error** cliff. Keep every design that cliff produced — the per-user write ceiling is still the only thing bounding a runaway client — but stop calling it an availability cliff. Cloudflare still has no hard spending cap, so bounding amplification is the whole posture. This rests on the owner's statement, not on a dashboard read: check the plan before quoting a number.
- **Features never reach the data layer directly** — and as of story 5-6 that is finally TRUE rather than aspirational, because it takes TWO `lint:layers` rules, one per primitive. **Rule 6:** `hono/client`'s `hc()` — the worker RPC client constructor — may be imported and called in exactly one module, `apps/expo/src/lib/api.ts`. **Rule 7:** `@/lib/api` may be imported (by any spelling, relative or type-only) by exactly one module, `apps/expo/src/lib/sync.ts` — the query module that owns the cache, the explicit invalidation and the write outbox. ⚠️ **Rule 6 alone never enforced this sentence**: its own self-test blesses a feature calling `api.health.$get()` directly, so between 5-4 and 5-6 a raw call from a component was green on every gate. Both rules **fail closed** if their chokepoint stops existing: between stories 5-2 and 5-4 the gate scanned for the retired vendor's `db.useQuery` and, that primitive having been deleted, reported clean forever. **Rule 8 (story 6-1):** `expo-sqlite` — the driver for the 4.2 MB Quran database bundled inside the app — may be imported, and a connection opened, in exactly one module, `apps/expo/src/lib/quranDb.ts`. ⚠️ **This sentence used to end "SQLite and MMKV access is centralised in `lib/` by convention, and that half is not gated; do not claim it is."** The SQLite half is gated now, and the honest reason it was not before is that until story 6-1 there was **nothing to gate**: `expo-sqlite` was a dependency with zero call sites, and a rule with no subject can only report clean. 6-1 created the first consumer and therefore the first thing a second consumer could bypass. What the rule buys is the Quran-text non-negotiable rather than tidiness — the chokepoint runs `PRAGMA query_only = ON`, exports no handle and offers no `exec` door, while a second `openDatabaseSync` anywhere else opens READWRITE (expo-sqlite has no read-only flag at all), typechecks, and is invisible to `pnpm verify`, which hashes the **repo's** copy at build time. Rule 8 fails closed like the other two. **MMKV access is still convention only; do not claim otherwise.**
- **`headerLeft` and `headerRight` are RESERVED WORDS in this codebase** (story 5-8), along with `unstable_header*Items` and `<Stack.Toolbar placement="left"|"right">` — all of which reach the same native stack header slot, where on an Apple-silicon Mac running the iPhone build a control is DRAWN and never receives a mouse click. tsc, jest, RNTL, Biome and screenshots are all blind to it. `lint:header-controls` is a flat PROHIBITION, not a routing shim — do not port `useHeaderControlSlots` — and `undefined` is its only allowance. Adding an exemption is an **owner call**; the map ships empty. ⚠️ **ARCHITECTURE §9 HAS NOW FLIPPED THREE TIMES AROUND THIS GATE AND THE GATE HAS NOT MOVED — judge it on the measured defect, never on the architecture of the day.** 2026-08-20 custom → 2026-08-26 native (on a running web build that disproved the web-rendering claim; **that claim is dead and must not drive a fourth flip**) → **2026-08-27 back to custom on all four platforms, which is CURRENT** (`sprint-change-proposal-2026-08-27.md`; the app draws its own header and tab bar, `NativeTabs` and the native stack header are gone, and **story 6-6 — sequenced before 6.3 — landed the migration: `AppHeader`'s slots are named `leading`/`trailing`**). Under custom chrome the defect becomes *impossible* rather than merely forbidden: there is no native header to install a control into. That is an argument FOR keeping the gate, not for relaxing it — it costs nothing and is the only thing between a future native header and a silently broken control. ⚠️ **The gate is an identifier match, so it fires on our OWN in-tree chrome props, which under custom chrome is the live case: name them `leading` / `trailing`, never a file exemption.** **Everything else — every spelling scanned, the four fail-closed floors, why the names are reserved and what to do about a third-party header prop — is in the docblock of `scripts/lint-header-controls.mjs`, which is the single source.**
